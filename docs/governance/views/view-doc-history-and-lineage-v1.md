# DOC History And Lineage v1

## Purpose

- This view is the bounded history surface for the `DOC` contract family.
- It exists so readers can understand how the current `DOC` surface emerged without replaying long source-owner logs end to end.
- It is not a second current front door, not a second promotion map, and not a replacement for retained source-owner chronology.

## Current Reading First

- Start at `docs/governance/views/view-doc-current-front-door-v1.md` when the question is `what is true now?`
- Then open the active `DOC` contract body for the area you need.
- Use this history view when the question is `how did the current DOC shape emerge?`
- Use retained source-owner logs when the question is `what exactly happened in detail?`

## Major Evolution Chain

1. `S0B-3A`
   - stable identifiers, frontmatter, and decoupled metadata become the base document-management grammar
2. `S0C-1A`
   - logs become structured decision surfaces instead of loose chronology
3. `S0D-1A`
   - parent spine plus child-log orchestration and the `P/C/S` ledger become the reusable execution model
4. `S0E-3A`
   - roadmap bridging makes milestone and log lineage machine-readable
5. `S0E-6A`
   - dual-track normalization separates automation-facing structure from human evidence ledger
6. `S0F-4A` + `S0F-4B` + `S0F-3I` + `S0F-4C`
   - the first `DOC` source-owner quartet concentrates role boundaries, source-log compatibility, taxonomy, and family-front-door transition
7. `S0F-4D`
   - the current `DOC` contract home and the first old-`GC-*` triage model are fixed explicitly
8. `S0F-4E`
   - the quartet is promoted into family-owned current `DOC` contracts
9. `S0F-4F`
   - reader surfaces are consolidated into the stable current `DOC` front door and promotion-map split
10. `S0F-4G`
   - the first durable `DOC` history surface and extraction-before-cleanup gate are fixed so history can be read through a stable family view instead of only through source-log archaeology

## Historical Milestones

| milestone | strongest source | why it matters now |
| --- | --- | --- |
| structure baseline | `S0B-3A` | current `DOC` contracts still rely on stable metadata and explicit document identity |
| structured log reading | `S0C-1A` | source-owner logs remain readable as decision-first history instead of loose notes |
| orchestration model | `S0D-1A` | parent and child logs inherit the reusable `P/C/S` execution shape |
| roadmap bridge | `S0E-3A` | lineage can be followed through explicit milestone and log links instead of prose-only breadcrumbs |
| automation versus evidence split | `S0E-6A` | current contracts and history surfaces can stay concise while detailed proof remains in retained evidence lanes |
| `DOC` source-owner concentration | `S0F-4A`, `S0F-4B`, `S0F-3I`, `S0F-4C` | the four rule families become explicit enough to promote cleanly |
| current `DOC` landing | `S0F-4D` | family-owned `DOC` contracts get a stable current home and old-`GC-*` cleanup gets a first bounded triage model |
| promotion event | `S0F-4E` | the source-owner quartet becomes the active `DOC` contract quartet |
| reader-surface consolidation | `S0F-4F` | current reading, mapping, and history can now stay separate instead of collapsing into one mixed summary |
| history publication gate | `S0F-4G` | the lineage view and extraction-before-cleanup rule become explicit enough that later history reading and cleanup no longer depend on ad hoc archaeology |
