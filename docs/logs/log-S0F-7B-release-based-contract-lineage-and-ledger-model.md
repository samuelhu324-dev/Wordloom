## Decision / Outcome

**Decision**:

- `S0F-7B` opens as the bounded follow-on lane after `S0F-7A` to replace the current chronology-first contract model with one explicit `family + release` model.
- This lane exists because `S0F-7A` made lineage readable, but the current template still overloads one sequence-bearing contract id to mean both `stable family identity` and `current contract content instance`.
- The immediate correction is to treat meaningful contract content change as one new release record, while moving `log/issue extraction routing` into one support-only ledger surface instead of forcing lineage fields to describe source slicing.

**Default choices (phase defaults / v1)**:

- Keep `docs/governance/contracts/` as the canonical contract root.
- Treat one contract family as the stable semantic lane, and one release record as one bounded effective content state inside that family.
- Treat `split`, `absorb`, `supersede`, and `retire` as contract-layer lineage only.
- Treat `what lines from logs/issues/support-only sources were routed into which contract release` as ledger work, not as lineage.
- Keep the first concrete sample fixed as `S0A-2A` after the model is defined, so the repo can test both the ledger split and one new release generated by absorption/update.

## Problem Statement

- The current `S0F-7A` template improved lineage, but it still leaves four unresolved pressures:
  - the sequence in `DOC-...-0001` currently reads as both category ordinal and effective content version
  - meaningful content updates still have no defended rule for when to create one new contract record versus rewrite one existing file
  - `source_refs` currently reads as minimal decisive source support, while newer discussion now also requires cumulative source carry-forward across later releases
  - there is no support-only ledger that records how one mixed source log or issue was split across multiple contract families, releases, or retained-only destinations
- Without a release-based model, later absorption, merge, split, and update work will keep overloading lineage verbs with source-routing meaning that does not belong there.

## Exported Sections / Outlet Ownership

- This slice starts as a `contract-model + support-only ledger` lane.
- The default expected landing is one revised contract template, one support-only ledger template, and one first sample ledger plus release packet after the model is accepted.

**Outlet ownership**:

- `contract`: expected landing surface for family/release model, revised lineage rules, and later release records
- `log-retained core`: expected landing surface for the bounded lane rationale, release-model rules, ledger rules, and evidence ledger
- `index/front-door`: possible later update so readers can distinguish family identity from release identity
- `view`: no-op by default; this lane fixes record semantics before opening new reader projections
- `runbook`: no-op by default; operator procedures are not the first landing here
- `support-only ledger`: expected landing surface for source-routing and extraction accounting

## Constraints

- Do not keep using lineage verbs to describe how raw log or issue paragraphs were split into different contract candidates.
- Do not treat every source edit as one in-place rewrite of the existing contract file if the effective contract meaning materially changes.
- Do not let later release records silently drop earlier absorbed sources from the cumulative history.
- Do not assume every absorbed source already exists as one contract; some source material will arrive from issue-only or log-only history and must therefore be accounted for in the ledger, not in `absorbed_from`.
- Do not reopen broad chronology-first rebuild ordering here; `7B` refines record semantics on top of `7A` rather than replacing `7A`'s chronology decision.

## Plan (draft)

### P1 (Family and release model)

- `P1-C1-S1`: define one stable `contract_family` field and one incrementing `contract_release` field
- `P1-C1-S2`: define when material content change requires one new release instead of one in-place rewrite
- `P1-C1-S3`: define how `0001`, `0002`, and later release numbers should be read across the same family

### P1-C1-S1 (Stable family identity and incrementing release identity fixed | v1)

- A `contract_family` now means the stable semantic lane for one governed rule set, such as `DOC-WORKFLOW-LABS`.
- A `contract_release` now means one bounded effective content state inside that family, such as `0001`, `0002`, or a later fixed-width release number.
- Under this rule, one full release record id should read as:
  - `<contract_family>-<contract_release>`
- This means the sequence is no longer read as the family's category ordinal; it is now read as the release counter inside one already-stable family.

### P1-C1-S2 (Material change requires one new release | v1)

- Create one new release instead of rewriting one existing release in place whenever at least one of these is true:
  - the effective rule meaning materially changes
  - the governed boundary materially expands, shrinks, or is redrawn
  - new source-owned content is absorbed strongly enough that the reader should treat the result as a new effective state
  - multiple earlier release states are consolidated into one later readable state
- Keep one in-place edit only when the effective meaning is unchanged, such as:
  - typo or wording cleanup
  - broken links or file-path corrections
  - formatting normalization
  - support-only clarification that does not change the owned rule meaning
- Under this rule, `meaning changed` defaults to `new release`; in-place rewrite becomes the narrow exception rather than the default habit.

### P1-C1-S3 (Release numbering semantics fixed | v1)

- `0001` now means `the first defended release in this family`, not `the permanent single contract file for this family`.
- `0002` and later numbers now mean `a later effective release of the same family`.
- Under this rule, readers should be able to infer one minimum chronology from numbering alone:
  - higher release number means later effective state within the same family
  - the family remains stable even when the release body changes materially
- A later release may therefore keep the same family while presenting one clearer current state that replaces, consolidates, or expands earlier releases.

### P2 (Release-based lineage semantics)

- `P2-C1-S1`: redefine `supersedes / superseded_by` as release-level successor links that may refer to multiple earlier releases
- `P2-C1-S2`: redefine `split_from / split_into` and `absorbed_from / absorbed_into` as contract-layer lineage only, not source-routing markers
- `P2-C1-S3`: define when one later release acts as merge, split-child, split-parent, absorption, or simple revision

### P3 (Support-only ledger model)

- `P3-C1-S1`: define the support-only ledger purpose and required routing columns
- `P3-C1-S2`: fix the ledger naming grammar as `ledger-<owner-lane-id>-<summary>.md`
- `P3-C1-S3`: define how one ledger records `source section -> target family/release action -> retained-only/no-contract` decisions

### P4 (Template revision)

- `P4-C1-S1`: revise the contract template to carry release metadata such as `contract_family`, `contract_release`, and one bounded release-change note
- `P4-C1-S2`: define when later releases must carry cumulative source references forward rather than shrinking the visible history
- `P4-C1-S3`: define how the effective body of one later release should contain both the new delta and the readable current state

### P5 (First sample on `S0A-2A`)

- `P5-C1-S1`: create one first support-only ledger for `S0A-2A`
- `P5-C1-S2`: create one new release sample that absorbs non-OPS material into the defended contract family
- `P5-C1-S3`: validate that the resulting release reads as both `what changed` and `what the current state now is`
