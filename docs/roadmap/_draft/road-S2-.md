## media / asset platform

方案 B：未来再升成单独层，但不叫 S7
如果未来 media 不只是“文件记录”，而是发展成一整套资产平台，例如：

blob/ref 生命周期
对象存储多后端
缩略图
OCR
内容审核
CDN
权限与签名 URL
保留策略、归档、销毁
审计与合规
这时候它已经不是一个普通模块，而是“数字资产平台”。

那时再升层比较合理，但我也不建议直接叫 S7 media。
更好的名字应该是按能力层命名，而不是按模块名命名。

例如：

S7 Asset Runtime
S7 Content Asset Platform
S7 Digital Asset Governance
其中最稳的是：

Asset Platform
Asset Runtime
因为这样以后不只装 media，还能装：

文档附件
导出包
备份对象
静态资源
审计附件
如果你只叫 media，会把层级名字绑死在“图片/视频”上，后面会不够用。

所以我的建议是
现在先不要新开 S7。
先把 media 定义为：

S1 邻接的独立模块
连接业务域和对象存储的资产管理层
如果以后它平台化得很明显，再升成：

Asset Platform
而不是直接叫 media。

一句话收口
现阶段：
media 适合作为 S1 下的独立横切模块，不建议直接变成 S7。

未来如果真要升层：
别叫 media，叫 Asset Platform 或 Digital Asset Platform 更合理。

什么时候需要微服务
这个问题最容易被误导。
结论先说：

大多数系统一开始都不需要微服务
微服务不是“高级架构”，而是“组织和交付复杂度已经高到单体扛不住时的拆分手段”
如果你现在还在整理 SoT、Projection、Ops、Media 这些边界，通常说明你更需要先把模块边界打稳，而不是先拆微服务
微服务到底是什么
最朴素的定义：

把一个系统拆成多个可独立部署、独立演进、通过网络通信协作的服务。

关键不是“代码分目录”，而是：

独立部署
独立运行
独立数据边界
网络调用协作
各自有明确责任
比如：

用户服务
内容服务
搜索服务
媒体服务
审计服务
它们不是一个进程，而是多个服务实例。

什么时候才真的需要微服务
我会用下面几个信号判断。

1. 团队规模和协作冲突已经很高
例如：

不同团队经常互相卡发布
一个模块改动会频繁影响别的模块
代码库太大，所有人都在改同一个地方
发布窗口越来越难协调
这本质上是组织问题，不是纯技术问题。

2. 某些模块的伸缩模式完全不同
例如：

搜索读流量很高
媒体转码特别吃 CPU
OCR/AI 特别吃 GPU
主业务写入很稳定，但异步处理很重
这时把它们拆开，才有独立扩缩容价值。

3. 某些模块的可靠性要求完全不同
例如：

主写路径必须强一致、低延迟
搜索允许短暂延迟
图片处理可以异步重试
审计服务必须强保留、强追踪
这时不同服务可以用不同 SLA 和故障隔离策略。

4. 技术栈差异已经真实存在
例如：

主系统是 Python
搜索管道更适合 Go/Java
OCR/AI 用 Python GPU 栈
前台 BFF 可能用 Node
但注意：技术栈不同本身不是拆服务理由，只有当收益明显大于运维成本才算。

5. 安全与合规边界必须隔离
这在政府和大企业更常见。

例如：

媒体原件访问权限很敏感
审计日志必须独立保留
某些数据必须在专门网段
某些服务只能内网访问
某些接口要走额外审批和审计
这时微服务或至少“独立部署边界”会更合理。

什么时候不该上微服务
这是更重要的部分。

如果你还处在下面这些阶段，通常不该急着上：

核心领域模型还没稳定
表结构和边界还在快速调整
团队规模很小
运维能力还不够
CI/CD、监控、追踪、发布治理都还没成熟
你现在主要痛点是模型混乱，而不是部署瓶颈
因为微服务会引入一整套额外成本：

服务发现
网关
重试
超时
分布式追踪
幂等
最终一致性
跨服务事务
部署编排
权限治理
如果单体内模块边界都还没理顺，拆成微服务通常会把混乱放大，而不是解决。

放到你现在这个项目里怎么判断
按你现在的语境，我会这样看：

当前更适合的是模块化单体
也就是：

library
bookshelf
book
block
media
chronicle
search
先在一个系统里把边界做清楚：

谁是 SoT
谁是 projection
谁是资产模块
谁是异步处理
谁只是 UI 消费
谁需要对象存储
谁需要审计
你仓库当前其实就在走这条路，而且这是对的。

未来最可能先拆出去的，不是主链路，而是这些边缘能力
如果以后要拆服务，我会优先考虑这几类：

Search service
Media asset service
Async worker / projection runtime
Audit / evidence service
而不是先把 library/book/block 拆得很碎。

原因很简单：

主链路通常耦合更深
搜索天然就是读模型边界
media 天然带对象存储、转码、权限
audit/evidence 天然适合更强隔离
也就是说，未来更合理的路线通常是：

先模块化单体
再把最外围、最独立、最异步的能力拆成服务

而不是一上来把每个业务对象都拆成服务。

如果 media 未来要不要做成微服务
答案是：

可以，但要等它先满足“平台化”信号。

比如当 media 开始出现这些需求：

多业务模块共用
多种文件类型
多存储后端
缩略图/转码/OCR
权限签发
生命周期管理
大量异步任务
独立扩容需求
这时 media 就很适合从“模块”演进成：

Asset Platform module
再进一步演进成 Asset Service
但在这之前，不要为了“看起来先进”而拆。

我会给你的实际判断标准
你以后可以用这个三步法判断一个东西要不要升层、要不要拆服务。

第一步：先问是不是独立能力线
如果只是一个业务对象，不升层。
如果是横跨多个模块的能力线，再考虑。

第二步：再问是不是已经平台化
如果只是“被很多地方用”，还不够。
如果它已经有自己独立的：

生命周期
存储策略
访问控制
异步任务
运维口径
才算平台化。

第三步：最后问是不是必须独立部署
如果不需要独立部署，就先保留为模块。
只有当独立部署真的带来明显收益时，才考虑微服务。
